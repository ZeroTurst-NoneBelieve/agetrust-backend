# #27 StatusList2021 리뷰 반영 범위

## 완료 범위와 외부 연동

이 문서는 #27 백엔드 변경의 동작과 검증 범위를 설명한다. 팀의 정책 승인이나
배포 완료를 뜻하지 않는다. 최신 커밋·CI·재리뷰 상태는 GitHub PR #43에서 확인한다.

- 백엔드는 VC 발급, 폐기 비트 갱신, 서명된 목록 제공 및 조건부 조회를 담당한다.
- [mobile #12 (K-6)](https://github.com/ZeroTurst-NoneBelieve/agetrust-mobile/issues/12)는
  [ADR-0013](https://github.com/ZeroTurst-NoneBelieve/agetrust-docs/blob/main/decisions/0013-vc-revocation-statuslist.md)의
  결과 절에 있는 "K-6 확장"과 연결된다. 키오스크의 목록 다운로드·갱신·검사 및
  오래된 캐시 경고가 해당 연동 작업이다. 현재 키오스크 구현은 아직 준비 전이다.
- 키오스크 연동을 #12에서 완료하기로 범위 분리 합의가 되거나 실제 연동을
  검증하기 전에는 `Closes #27`로 이슈 전체를 자동 종료하지 않는다.
- 연동 담당자에게 전달할 현재 API 동작과 테스트 순서는
  [키오스크 연동 안내](status-list-kiosk-handoff.md)에 정리한다.

## 인덱스 배정과 잠금

- `secrets`로 후보를 뽑고 같은 목록에서 이미 사용한 인덱스인지 확인한다.
  폐기·만료된 VC의 자리도 다시 사용하지 않는다.
- 32회 충돌하면 실제 미사용 인덱스 집합에서 무작위로 선택한다.
  재시도 소진만으로 `status list is full`을 반환하지 않는다.
- 목록이 실제로 가득 찼을 때만 503을 반환한다. 다음 목록으로 자동 전환하는
  기능은 아직 구현하지 않았다.
- advisory transaction lock은 목록 생성뿐 아니라 사용 여부 확인부터 VC 저장과
  commit까지 유지한다. 확인 직후 잠금을 풀면 다른 요청이 같은 빈자리를 배정할
  수 있다. 현재 전역 발급 직렬화는 의도된 안전장치다. 처리량 최적화는 인덱스
  예약·충돌 재시도와 트랜잭션 구조를 함께 설계하는 후속 작업으로 남긴다.

## URL 호환성

- 정식 조회 경로와 새 목록의 URL은 `GET /api/v1/status-lists/{id}`다.
- 이미 발급된 VC를 깨뜨리지 않도록 기존 `GET /api/v1/status/{id}`도 같은
  핸들러로 제공한다. 기존 경로는 OpenAPI에서 숨긴 호환 별칭이다.
- 기존 DB의 `status_list_url`이나 이미 서명된 VC는 변경하지 않는다. 따라서
  기존 목록을 재사용하는 새 발급도 그 목록에 저장된 기존 URL을 계속 사용한다.
  새 경로에서도 조회할 수 있지만 JWT 내부의 목록 ID는 저장된 URL과 일치한다.
- 모든 URL을 정식 경로로 바꾸는 데이터 이관은 이번 변경에 포함하지 않는다.

## 인증: 등록된 ACTIVE 키오스크만 조회

2026-09-08 작업자 요청에 따라 기존 `get_current_kiosk`를 정식/호환 경로 모두에
연결했다. 이후 #42의 계약에 맞춰 Bearer로 통일하기로 결정하여 아래와 같이 변경했다.
이 로컬 구현은 배포 완료를 뜻하지 않는다. 다른 담당자의 작업 일정은 별도로 조율한다.

- 요청 헤더는 `Authorization: Bearer <api_key>`다. API Key 원문만 보내며
  `kiosk_identifier:`를 앞에 붙이지 않는다. 기존 `X-Kiosk-Key`만 보내면 401이다.
  기존 헤더로의 fallback도 없다.
- API Key의 SHA-256 해시로 `kiosks.api_key_hash`를 조회해 키오스크를 찾고
  `ACTIVE`인지 매 요청 확인한다. GET에는 식별자 본문이나 별도 식별자 헤더가 필요 없다.
  사용자/관리자 로그인 JWT는 키오스크 키를 대신하지 않는다.
- 현재 DB에는 키 해시 UNIQUE 제약이 없으므로 같은 키가 여러 키오스크에 등록돼 있으면
  임의의 키오스크를 선택하지 않고 401 `KIOSK_KEY_INVALID`로 거부한다. 키별 테이블과
  검색 인덱스/제약 정비는 별도 키 관리 작업으로 남긴다.
- 키 누락·오류·미등록은 401 `KIOSK_KEY_INVALID`, 올바른 키를 가진 비활성/폐기
  키오스크는 401 `KIOSK_INACTIVE`다. 오류 응답은 `no-store`와
  `WWW-Authenticate: Bearer`로 반환한다.
- 인증은 목록 존재 확인과 304 판단보다 먼저 실행한다. Swagger에도 API Key 인증을 표시한다.
- DB 구조나 마이그레이션은 변경하지 않았다. 키 생성/배포/회전용 관리 API는 이번 범위가
  아니며 운영 키를 자동 생성하거나 개발 DB에 테스트 키를 심지 않았다.
- #42의 예정된 Bearer 헤더 계약과 맞춘 것이다. #42 결과 기록 API 자체를 구현한 것은
  아니다. 그 API를 구현할 때 인증된 키오스크와 본문의 `kiosk_identifier`가 같은지
  반드시 확인해야 한다. A의 키로 B의 결과를 저장할 수 있어서는 안 된다.
- 이 결정은 키오스크 담당자에게 요청 예시와 함께 공유한다. 키 발급·회전 관리 기능은
  #42에서도 별도 작업으로 분리한 범위다. ADR-0010의 발급/현장 주입안을 참고하고,
  실제 키 수령·설치 담당자와 전달 절차 및 일정은 별도로 조율한다.

목록에는 이름·생년월일·사용자 ID 또는 사람과 인덱스를 연결하는 표가 없다. 다만
encodedList는 암호화가 아니므로 비트를 읽을 수 있고, 특정 VC의 URL과 인덱스를 아는
사람은 그 VC의 폐기 상태를 알 수 있다. 공개 읽기가 곧 목록 수정 권한을 주는 것은
아니지만, 우리 서비스에서 조회 대상을 제한하기 위해 인증을 적용했다.
서명 검증과 키오스크의 목록 갱신은 API Key 인증을 붙여도 별도로 필요하다.

## 목록 검증과 HTTP 캐시

- 응답 서명 전에 패딩 없는 base64url 문자와 비트열을 검증해 잘못된 문자,
  gzip 오류와 최소 16KB 미만의 목록을
  거부한다. NULL·빈 값·손상 값은 503과 `Cache-Control: no-store`를 반환한다.
  잘못된 목록을 전부 0인 목록으로 대체하지 않는다.
- 검증은 304 판단보다 먼저 실행한다. 손상된 DB 상태를 304로 재검증하지 않는다.
- `If-None-Match`가 현재 weak ETag와 일치하면 본문 없는 304를 반환한다.
  강한/약한 태그 비교, 여러 태그·헤더, `*`를 지원한다. ETag에는 버전과 함께
  발급자 DID·목록 URL·목적·내용의 fingerprint를 넣는다.
- 200/304에는 `Cache-Control: private, no-cache`와 `Vary: Authorization`을 붙인다.
  공유 HTTP 캐시는 저장하지 못하고, 개인 HTTP 캐시도 재사용 전에 서버에서 인증 및
  재검증한다. `no-cache`는 저장 금지가 아니므로 ETag/304는 계속 사용할 수 있다.
  키오스크 앱의 별도 검증 목록 저장과 오프라인 사용 정책, 갱신 스케줄은 별개다.
- 배포 전 CDN/프록시에 남은 기존 `public, max-age=300` 응답은 제거하거나 만료를
  확인해야 한다. 새 헤더로 이미 내려받은 목록까지 회수할 수는 없다. HTTPS와 프록시의
  캐시 설정을 함께 확인하고, API Key를 URL·로그에 남기지 않는다.
- `updated_at`은 목록 데이터의 마지막 변경 시각이다. SQLAlchemy UPDATE 시
  갱신되며, 같은 비트를 다시 폐기해 변화가 없으면 갱신하지 않는다. DB 트리거가
  아니므로 직접 SQL로 수정할 때는 별도로 갱신해야 한다. DB 스키마 변경은 없다.
- 목록이 오래 변경되지 않았다는 사실과 캐시가 오래됐다는 사실은 다르다.
  키오스크 캐시 나이는 마지막 성공 조회 또는 304 재검증 시점을 기준으로 관리해야
  한다. JWT의 `iat`도 304 응답 시 새로 발급되지 않으므로 그 용도로 대체할 수 없다.
- 목록 JWT에 `exp`를 넣어 오프라인 인증을 강제 중단하는 변경은 하지 않는다.
  오래된 캐시로 인증을 계속하는 정책에는 폐기가 늦게 반영될 위험이 남는다.

HTTP 조건부 요청 의미: [RFC 9110 §13.1.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.2).
캐시 지시어 의미: [RFC 9111 §5.2.2](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2).

## 계약 확인 및 #44 적용 순서

- 2026-09-08 확인한 원격 ADR-0013은 제안 상태와 갱신 주기 1시간을 표시하지만,
  PR 리뷰는 승인된 ADR과 5분 주기를 언급한다. 최신 승인 근거 또는 문서 갱신을
  확인하기 전까지 키오스크 갱신 주기를 확정된 계약으로 안내하지 않는다.
- 인증 도입으로 HTTP 캐시는 서버 재검증을 요구하도록 바꿨다. 이 헤더는
  키오스크 앱의 다운로드 주기를 정하거나 오프라인 폐기 즉시 반영을 보장하지 않는다.
- #44는 아직 머지되지 않아 이 브랜치에 가져오지 않았다. 머지된 `dev`를 반영할
  때 StatusList의 404·503도 `detail.code`와 오류 스키마에 맞춘다. 손상 응답의
  `Cache-Control: no-store`와 #27 회귀 테스트를 유지해야 한다.

## 로컬 최종 검증 (2026-09-08)

- Windows Python 3.12와 격리된 PostgreSQL 15에서 ruff 및 전체 테스트 145개 통과,
  스킵 0개. 구성은 단위 138개 + 백엔드 E2E 3개 + PostgreSQL 회귀 4개다.
- `alembic upgrade head` 성공, `alembic check`에서 새 스키마 변경 없음.
- E2E는 ASGI 인프로세스 HTTP 요청과 실제 PostgreSQL을 사용한다. 실제 키오스크
  앱, 물리 네트워크, CI Python 3.11에서 이번 로컬 수정본을 검증했다는 뜻은 아니다.
- 이번 마무리에서 잘못된 base64url 문자를 조용히 무시하는 경로도 차단했다.
  서명 전 및 조건부 조회 시 503/no-store를 반환하는 회귀 검증을 포함한다.
- 인증 회귀는 Bearer 전환 후 16개다. 실제 PostgreSQL E2E에서도 테스트 전용 키오스크로
  두 경로의 인증 성공·실패, 비활성/폐기 후 304 차단 및 기존 VC 폐기 흐름을 검증했다.
- Bearer 원문만으로 키 해시 조회, 이전 X 헤더/로그인 JWT 거절, 서로 다른 키의
  키오스크 식별, 중복 키 해시 거절 및 중복 해소 후 정상 재검증도 확인했다.
